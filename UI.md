# Runtime UI integration

`Content/Mods/PalworldPinItems/WBP_PinItems.uasset` is a UE 5.1.1 Widget Blueprint with a transparent canvas and a top-right bordered panel. Its exposed widget variables are `Panel`, `HoverName`, `PinButton`, `PinLabel`, `PinnedText`, and `ClearButton`. A bounded scroll area keeps long pin lists inside the screen.

Native `PinButton.OnClicked` calls the Blueprint function `PinHovered`; `ClearButton.OnClicked` calls `ClearPins`. `Scripts/main.lua` hooks those two functions with UE4SS after loading the widget class. The Blueprint contains no Pal SDK classes and can be cooked in the standalone `PalworldPinItems.uproject`.

The Lua integration reads `PalHUDInGame.HoverWidget.CachedDisplayInfo`, declared as `PalUICommonItemInfoDisplayData` in the SDK. That struct supplies `RecipeID`, `RecipeRequiredItemsOverrideMap`, and `ItemInfo.ItemId.StaticId`. Crafting costs come from `PalMasterDataTablesUtility.GetItemRecipeDataTableAccess` and `PalMasterDataTableAccess_ItemRecipe.BP_FindRow`. B-menu data comes from a hovered `WBP_IngameMenu_Construction_Icon` (or its `WBP_PalInvisibleButton`) and its `MyBuildObjectData` row. This takes priority over stale crafting tooltips. The menu's `LastHoveredBuildObjectWidget` soft reference is not used. Other building item tooltips resolve their IDs through `PalMapObjectUtility.ConvertBlueprintItemIdToBuildObjectId`.

Unreal return structs are copied to plain Lua data before pinning. Costs are read at pin time and stay available after the originating menu or tooltip is destroyed. Each refresh reads `PalPlayerController.GetPalPlayerState().GetInventoryData().CountItemNum` for the pinned materials and displays needed/owned. Duplicate materials across pins share a count lookup within that refresh. Personal inventory is counted; base storage is excluded. A missing inventory is displayed as `?`, never a fabricated zero. Only the local player's UI is affected. No crafting or server RPCs are invoked.

Authoring mount: PMK's `Content/Mods/PalworldPinItems` is a junction to this project's corresponding Content directory. This leaves asset ownership in the mod folder. `Build.ps1` uses Unreal's `CookSinglePackageNoRefs` mode on the mod directory and mounts its pak at `../../../Pal/Content/Mods/PalworldPinItems/`. The widget uses native UMG classes and default engine fonts supplied by Palworld; the cook skips default maps, global shader output, and referenced engine packages. Every custom asset must stay inside the mod's cooked directory. No original game assets are redistributed.

Item labels use `PalUIUtility.GetItemName` only after `PalUtility.GetItemIDManager().GetStaticItemData` confirms a valid item. `BP_FindRow.bResult` must succeed before a returned recipe row is read. These guards prevent invalid IDs (including `None`) from returning a null FText to UE4SS's native `ToString`, which aborts outside Lua error handling. A building with no blueprint item uses its building ID as its label. No item names or costs are hardcoded.

On 2026-10-10, Unreal cooked the widget with zero errors and warnings. The first live test confirmed Lua startup, button hooks, widget creation, and workbench pinning, and exposed a B-menu hover failure. The subsequent run aborted in UE4SS's FText conversion before the user could test the corrected features. Invalid recipe/name lookup regressions failed before the guards and pass after them. Construction-icon detection, safe UObject validity checks, and live inventory counts also have regression coverage. After installation of the guards, the user confirmed both menus and updating needed/owned counts work without crashing; runtime logs record building and crafting pins. Palworld Blueprint property/function names can change with game updates. Graphify cannot parse the binary Widget Blueprint; this document records its structure and event relationships instead.
