# Runtime UI integration

The UI uses five UE 5.1.1 Widget Blueprints in `Content/Mods/PalworldPinItems`. Graphify cannot parse these binary assets; this document records their structure and integration instead.

## Widget layout and events

`WBP_PinItems` is the top-right HUD panel. `RootCanvas` contains `Panel`, a fixed-width 334-pixel navy border with an amber `Header` and `Heading`. `Content` contains `HoverName`, `PinButton`/`PinLabel`, `PinnedList`, and `ClearButton`/`ClearLabel`. Text uses regular engine fonts at 10–13 pixels. The body color is linear RGBA (0.025, 0.05, 0.11, 0.92), and the header is (1, 0.407, 0.021, 1). There is no ScrollBox. `PinButton.OnClicked` calls `PinHovered`; `ClearButton.OnClicked` calls `ClearPins`. Lua hooks these ordinary Blueprint functions.

`WBP_PinCard` has a 314-pixel `CardWidth` and vertical `CardBody`. `TitleRow` contains a 24-pixel `ItemIcon` and 13-pixel `ItemName`. `Materials` holds up to five ingredient rows. `WBP_PinMaterial` is a 304-by-20-pixel row with an 18-pixel `MaterialIcon`, 11-pixel `MaterialName`, and 14-pixel green `Complete` image. Canvas content uses automatic desired sizing. Hidden checkmarks retain their alignment space; unused cards and rows collapse.

`WBP_PinTab` adds a navy `OpenButton` labeled Pinned to the runtime main menu's `HorizontalBox_Tab`. Its click calls `OpenPinned`. `WBP_PinPage` is a centered 520-pixel navy page with an amber `PageHeading`, `PinnedList`, `PageNavigation`, and `CloseButton`. Previous/Next buttons call `PreviousPage`/`NextPage`; Close calls `ClosePinned`. The page has five cards, a page indicator, and no scrolling. Selecting a native tab through `SelectByMainMenuType` hides the page; closing the player menu also hides it. The added entry does not extend the native tab enum: click it directly, since native tab-cycling keys skip this entry. The native menus remain intact underneath the additional page.

## Runtime data and rendering

`Scripts/main.lua` owns hover detection, pin actions, and game-thread refresh. `Scripts/inventory.lua` owns inventory-event subscriptions and cached reads. `Scripts/storage.lua` owns current-base storage snapshots and subscriptions. `Scripts/recipes.lua` copies returned Unreal structs into plain Lua recipe snapshots. Pins use an ordered array for page indexing and a hash table for membership, with a version increment on changes. `Recipes.display` returns at most five cards for a clamped page, retaining every pin in the session tracker. HUD rendering uses page one; the Pinned view can page through the rest. Material text is owned/needed, and completion means owned is at least the requirement. Unknown inventory displays `?` and never shows a completion check.

Performance: the local controller comes from `GameplayStatics.GetPlayerController` using `UEHelpers.GetGameViewportClient` as world context. One `NotifyOnNewObject` listener on `/Script/UMG.UserWidget` tracks construction icons, crafting tooltips, and main menus by class name. One bootstrap scan per tracked class supports existing UI; periodic updates use cached instances and prune destroyed objects. Hover detection returns immediately without an overlay. Only one periodic game-thread callback can be queued. Text, visibility, and enabled values are cached by native widget address so fresh Lua wrappers do not cause repeated native writes. UI creation resets those caches to handle reused addresses. Measurements and pending in-world verification are in `PERFORMANCE.md`.

`Scripts/ui.lua` creates the five cards and their material rows, updates visibility/text/checks, and caches icon bindings until a row's item changes. Crafting and material icons use `PalStaticItemDataBase.IconTexture` through `PalUtility.GetItemIDManager().GetStaticItemData`. Building snapshots capture the hovered construction icon's texture path, with `PalMasterDataTablesUtility.GetBuildObjectIconDataTableAccess`/`BP_FindRow` and its `SoftIcon` as fallback. Completion uses the game's `/Game/Pal/Texture/UI/Main_Menu/T_prt_itemslot_select_check_0` texture, tinted green. All game textures are referenced at runtime and are not redistributed.

Crafting data comes from `PalHUDInGame.HoverWidget.CachedDisplayInfo`, including `RecipeID`, `RecipeRequiredItemsOverrideMap`, and `ItemInfo.ItemId.StaticId`. Costs use `GetItemRecipeDataTableAccess`/`BP_FindRow`. B-menu detection reads hovered `WBP_IngameMenu_Construction_Icon` or `WBP_PalInvisibleButton` and `MyBuildObjectData`, taking priority over stale crafting tooltips. Other building tooltips resolve through `PalMapObjectUtility.ConvertBlueprintItemIdToBuildObjectId`. Costs remain usable after the original tooltip is destroyed.

Personal counts use `PalPlayerController.GetPalPlayerState().GetInventoryData().CountItemNum` only for uncached visible material IDs. Duplicate materials share a persistent hash lookup across HUD and menu pages; zero is cached too. The Lua mod never iterates personal inventory slots. PMK supplies only a stub for this native count function, so its internal complexity is unknown.

Storage counts use `PalUtility.GetPlayerCharacter(controller).InsideBaseCampCheckComponent` to identify the current base, keyed by its four-field GUID. `PalItemUtility.CollectLocalPlayerControllableAllItemInfos(controller, out_infos, BaseCampOnly)` supplies one bulk base-only collection. Lua immediately copies item IDs and numbers into a hash map and sums duplicate rows; each visible material adds one cached storage total to its cached backpack total. An absent material contributes zero; an unavailable backpack remains unknown. Counts and completion checks change on entering, leaving, or switching bases. The HUD's `HoverName` shows `Backpack` or `Backpack + <base name>` when no recipe is hovered; `WBP_PinPage.PageHeading` shows the same scope. No widget asset changes are needed.

`PalBaseCampModuleItemStackInfo` update/replication/container/lock/security callbacks invalidate only the matching current base. Explicit `PalNetworkBaseCampComponent.RequestReplicateBaseCampItemStackInfo_ToServer` requests use a detached GUID to start/stop storage metadata updates for that base. The mod uses the controller's `Transmitter.GetBaseCamp()` component, never discovers chests globally or moves inventory items. A subscription release waits until any native menu overlay closes; a native cancellation for active pins is resumed on the next update. Recovery also renews metadata updates. Clearing pins stops base lookups and snapshots after any deferred release; changing controller or leaving the in-game HUD clears the scope. Base/cache versions participate in the existing redraw gate. Design and validation limits are documented in `BASE_STORAGE.md`.

Native post-hooks observe `PalPlayerInventoryData.OnUpdateInventoryContainer`, `OnUpdateEssentialContainer`, `OnUpdateLoadoutSlot`, `OnUpdateEquipmentSlot`, and `OnRep_InventoryInfo`, plus `PalItemContainerMultiHelper.OnUpdateContainerContent` and `OnRep_Containers`. Callbacks filter by the active local inventory or its `InventoryMultiHelper` native address and mark the cache dirty; they do not count or touch UI inline. The next game-thread refresh invalidates counts once for the whole notification burst. Changing inventory owner also invalidates counts. A ten-second reconciliation recovers missed events, reduced to one second if no event handlers are available. The cache and pin versions suppress unchanged HUD/page model generation and card redraws; opening or changing a page draws it and queries only newly visible uncached ingredients. Hidden pins are not polled.

Only local UI and read-only storage metadata subscriptions change; no crafting or item-movement RPCs are called. Item-name lookups require valid static item data before `PalUIUtility.GetItemName`; recipe rows require `BP_FindRow.bResult`. These guards avoid a null FText reaching UE4SS's native ToString. Buildings without a valid item label fall back to their building ID.

Local hosts (`controller:HasAuthority()`) already have storage state and skip metadata network-component access and requests. The first storage test exposed a native null-pointer dereference inside the subscription RPC; the authority guard also applies to deferred releases. Host fixtures reject that unsafe path and retain base counts, scope changes, and cached rendering. On 2026-10-10, the user confirmed crash-free pinning, correct chest counts, and no observed FPS drops after the patch, and authorized publishing. A second-base gameplay test, remote multiplayer, and private/locked-chest permission checks remain pending; see `BASE_STORAGE.md` for the dump evidence.

## Authoring, packaging, and validation

PMK's `Content/Mods/PalworldPinItems` junction points to the mod's owned Content directory. `Build.ps1` explicitly cooks all five owned packages using `CookSinglePackageNoRefs` and mounts the pak at `../../../Pal/Content/Mods/PalworldPinItems/`. Widgets use native UMG and game-supplied engine fonts. Build and install include every Lua module, including `ui.lua`. ZIP creation is opt-in and requires the user's request. The standalone Windows cooking project disables the unused AndroidFileServer plugin so it does not generate a local security token into versioned configuration.

On 2026-10-10, all five Widget Blueprints compiled, and cooking completed with zero errors or warnings. Lua regression tests cover recipe snapshots, icons, owned/needed text, changing completion state, the five-card cap, retained additional pins, paging, tab injection, and menu closure. The prior version's workbench/B-menu pinning and live inventory counts were confirmed in-game after the FText crash fix. The user confirmed the redesigned UI works in-game, specifically that the HUD shows only five pins and the Pinned entry exposes six or more saved pins. Runtime logs confirm crafting pins, tab injection, and the Pinned view opening without mod errors. Palworld widget names and reflected signatures can change with game updates.
