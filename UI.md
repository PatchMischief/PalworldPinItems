# Runtime UI integration

The UI uses five UE 5.1.1 Widget Blueprints in `Content/Mods/PalworldPinItems`. Graphify cannot parse these binary assets; this document records their structure and integration instead.

## Widget layout and events

`WBP_PinItems` is the top-left HUD panel above the bottom-left Pal icons. `RootCanvas` contains `Root`, whose `Panel` canvas slot anchors at (0, 0), aligns at (0, 0), and offsets (60, 40). This places its top at y=40 and its left at x=60 in the supplied 1920x1080 reference. `Panel` is a fixed-width 334-pixel navy border with an amber `Header` and `Heading`. `Content` contains `HoverName`, `PinButton`/`PinLabel`, `PinnedList`, and `ClearButton`/`ClearLabel`. Text uses regular engine fonts at 10–13 pixels. The body color is linear RGBA (0.025, 0.05, 0.11, 0.82), and the header is (1, 0.407, 0.021, 1). There is no ScrollBox. `PinButton.OnClicked` calls `PinHovered`; `ClearButton.OnClicked` calls `ClearPins`. Lua hooks these ordinary Blueprint functions. The slot targets the reference layout rather than inspecting native Pal widgets; other HUD settings/list sizes need a visual gameplay check.

`WBP_PinCard` has a 314-pixel `CardWidth` and vertical `CardBody`. `TitleRow` contains a 24-pixel `ItemIcon`, a 13-pixel `ItemName` with Fill sizing and ClipToBounds, and a 20-by-20 `RemoveSize` containing a red rounded `RemoveButton` with white 10-pixel `RemoveLabel` text X. The button sits at the far right with six pixels of left padding; its OnClicked calls the Blueprint function `RemovePin`. `Materials` holds up to five ingredient rows. `WBP_PinMaterial` is a 304-by-20-pixel row with an 18-pixel `MaterialIcon`, 11-pixel `MaterialName`, and 14-pixel green `Complete` image. Canvas content uses automatic desired sizing. Hidden checkmarks retain their alignment space; unused cards and rows collapse.

`WBP_PinTab` adds a navy `OpenButton` labeled Pinned to the runtime main menu's `HorizontalBox_Tab`. Its click calls `OpenPinned`. `WBP_PinPage` is a centered 520-pixel navy page with background alpha 0.85 (previously 0.97) with an amber `PageHeading`, `PinnedList`, `PageNavigation`, and `CloseButton`. Previous/Next buttons call `PreviousPage`/`NextPage`; Close calls `ClosePinned`. The page has five cards, a page indicator, and no scrolling. Selecting a native tab through `SelectByMainMenuType` hides the page; closing the player menu also hides it. The added entry does not extend the native tab enum: click it directly, since native tab-cycling keys skip this entry. The native menus remain intact underneath the additional page.

## Runtime data and rendering

`Scripts/main.lua` owns hover detection, pin actions, and game-thread refresh. `Scripts/inventory.lua` owns inventory-event subscriptions and cached reads. `Scripts/storage.lua` owns current-base storage snapshots and subscriptions. `Scripts/recipes.lua` copies returned Unreal structs into plain Lua recipe snapshots. Pins use an ordered array for page indexing and a hash table for membership, with a version increment on changes. `Recipes.remove(key)` removes exactly the matching pin and is shared by toggling and X-button actions. Each card retains its displayed recipe key; the click hook compares the source's native address against the ten current HUD/page cards, then removes that bound key independently of hover. Removing the final pin on a page clamps paging through the existing display function. Stale/unknown widget clicks do not remove a pin.

`Recipes.display` returns at most five cards for a clamped page, retaining every pin in the session tracker. HUD rendering starts with page one, then `UI.fit_hud` forces a layout prepass and collapses whole trailing cards until the panel's desired height fits 73% of the DPI-adjusted viewport height minus 48 pixels. The panel starts 40 pixels below the top and ends eight pixels above the 73% screen-height boundary, before the bottom-left Pal icons in the reference. The header reports shown/total when pins overflow; all pins remain in the Pinned page. Font size and ingredient rows are preserved, with no clipping of full cards or scrollbar. Fitting is bounded to five removals and runs only on data/hover/viewport-height changes; unchanged updates do not prepass cards. Material text is owned/needed, and completion means owned is at least the requirement. Unknown inventory displays `?` and never shows a completion check.

Performance: the local controller comes from `GameplayStatics.GetPlayerController` using `UEHelpers.GetGameViewportClient` as world context. One `NotifyOnNewObject` listener on `/Script/UMG.UserWidget` tracks construction icons, crafting tooltips, and main menus by class name. One bootstrap scan per tracked class supports existing UI; periodic updates use cached instances and prune destroyed objects. Hover detection returns immediately without an overlay. One persistent `LoopInGameThreadWithDelay(150, ...)` timer runs updates, avoiding recurring async Lua execution and callback queuing. X clicks only remove the bound recipe; versioned rendering happens on the next timer update after Slate's click dispatch ends. Text, visibility, and enabled values are cached by native widget address so fresh Lua wrappers do not cause repeated native writes. UI creation resets those caches to handle reused addresses. Measurements and pending in-world verification are in `PERFORMANCE.md`.

The first live X-button test on 2026-10-11 froze. The last log error unexpectedly identifies the scheduled update closure as the storage hook's `context:get()` method and reports an invalid `xpcall` argument. No frozen-process dump was available because Palworld had closed by inspection. UE4SS's installed source shares `hook_lua` between hooks and scheduled actions; [its maintainer identifies async Lua as unsafe](https://github.com/UE4SS-RE/RE-UE4SS/issues/1345). The mod's recurring async scheduling was removed. Independently, X redraw is deferred because immediate refresh hides/rebinds the clicked card and forces layout while its click dispatch is still active. This protects against reentrant layout, but the log alone does not prove which hazard caused the freeze. Regression checks reject `LoopAsync`, require exactly one game-thread timer, require zero UI writes/prepasses inside the X handler, exercise HUD/page removal after the next update, and confirm recovery after an injected update error. On 2026-10-11, the user confirmed the patched X works; logs show removals and continued pin/hover activity without errors. Page-2 removal has automated coverage but no separate user confirmation.

`Scripts/ui.lua` creates the five cards and their material rows and updates visibility/text/checks using the original UI-and-shortcut revision's icon-binding path. The user requested removal of the subsequent performance experiment on 2026-10-11: ordinary-Lua material-icon caching and the shared default-utility cache are removed. Crafting and material icons use `PalStaticItemDataBase.IconTexture` through `PalUtility.GetItemIDManager().GetStaticItemData`. Building snapshots capture the hovered construction icon's texture path, with `PalMasterDataTablesUtility.GetBuildObjectIconDataTableAccess`/`BP_FindRow` and its `SoftIcon` as fallback. Completion uses the game's `/Game/Pal/Texture/UI/Main_Menu/T_prt_itemslot_select_check_0` texture, tinted green. All game textures are referenced at runtime and are not redistributed.

Crafting data comes from `PalHUDInGame.HoverWidget.CachedDisplayInfo`, including `RecipeID`, `RecipeRequiredItemsOverrideMap`, and `ItemInfo.ItemId.StaticId`. Costs use `GetItemRecipeDataTableAccess`/`BP_FindRow`. B-menu detection reads hovered `WBP_IngameMenu_Construction_Icon` or `WBP_PalInvisibleButton` and `MyBuildObjectData`, taking priority over stale crafting tooltips. Other building tooltips resolve through `PalMapObjectUtility.ConvertBlueprintItemIdToBuildObjectId`. Costs remain usable after the original tooltip is destroyed.

Personal counts use `PalPlayerController.GetPalPlayerState().GetInventoryData().CountItemNum` only for uncached visible material IDs. Duplicate materials share a persistent hash lookup across HUD and menu pages; zero is cached too. The Lua mod never iterates personal inventory slots. PMK supplies only a stub for this native count function, so its internal complexity is unknown.

Storage counts use `PalUtility.GetPlayerCharacter(controller).InsideBaseCampCheckComponent` to identify the current base, keyed by its four-field GUID. `PalItemUtility.CollectLocalPlayerControllableAllItemInfos(controller, out_infos, BaseCampOnly)` supplies one bulk base-only collection. Lua immediately copies item IDs and numbers into a hash map and sums duplicate rows; each visible material adds one cached storage total to its cached backpack total. An absent material contributes zero; an unavailable backpack remains unknown. Counts and completion checks change on entering, leaving, or switching bases. The HUD's `HoverName` shows `Backpack` or `Backpack + Base <number>, falling back to Backpack + current base for names without ASCII digits` when no recipe is hovered; `WBP_PinPage.PageHeading` shows the same scope. No widget asset changes are needed.

`PalBaseCampModuleItemStackInfo` update/replication/container/lock/security callbacks invalidate only the matching current base. Explicit `PalNetworkBaseCampComponent.RequestReplicateBaseCampItemStackInfo_ToServer` requests use a detached GUID to start/stop storage metadata updates for that base. The mod uses the controller's `Transmitter.GetBaseCamp()` component, never discovers chests globally or moves inventory items. A subscription release waits until any native menu overlay closes; a native cancellation for active pins is resumed on the next update. Recovery also renews metadata updates. Clearing pins stops base lookups and snapshots after any deferred release; changing controller or leaving the in-game HUD clears the scope. Base/cache versions participate in the existing redraw gate. Design and validation limits are documented in `BASE_STORAGE.md`.

Native post-hooks observe `PalPlayerInventoryData.OnUpdateInventoryContainer`, `OnUpdateEssentialContainer`, `OnUpdateLoadoutSlot`, `OnUpdateEquipmentSlot`, and `OnRep_InventoryInfo`, plus `PalItemContainerMultiHelper.OnUpdateContainerContent` and `OnRep_Containers`. Callbacks filter by the active local inventory or its `InventoryMultiHelper` native address and mark the cache dirty; they do not count or touch UI inline. The next game-thread refresh invalidates counts once for the whole notification burst. Changing inventory owner also invalidates counts. A ten-second reconciliation recovers missed events, reduced to one second if no event handlers are available. The cache and pin versions suppress unchanged HUD/page model generation. A changed cache version redraws the visible cards; the experiment's additional detached-value comparison is removed at the user's request. A height change still refits the HUD; opening or changing a page queries only newly visible uncached ingredients. Hidden pins are not polled.

Only local UI and read-only storage metadata subscriptions change; no crafting or item-movement RPCs are called. Item-name lookups require valid static item data before `PalUIUtility.GetItemName`; recipe rows require `BP_FindRow.bResult`. These guards avoid a null FText reaching UE4SS's native ToString. Buildings without a valid item label fall back to their building ID.

Local hosts (`controller:HasAuthority()`) already have storage state and skip metadata network-component access and requests. The first storage test exposed a native null-pointer dereference inside the subscription RPC; the authority guard also applies to deferred releases. Host fixtures reject that unsafe path and retain base counts, scope changes, and cached rendering. On 2026-10-10, the user confirmed crash-free pinning, correct chest counts, and no observed FPS drops after the patch. On 2026-10-11, the user also confirmed correct counts across two bases. Remote multiplayer and private/locked-chest permission checks remain pending; see `BASE_STORAGE.md` for the dump evidence. The HUD-position/X-button patch has separate automated resize/removal/idle checks; the user confirmed patched X removal on 2026-10-11.

## Authoring, packaging, and validation

PMK's `Content/Mods/PalworldPinItems` junction points to the mod's owned Content directory. `Build.ps1` explicitly cooks all five owned packages using `CookSinglePackageNoRefs` and mounts the pak at `../../../Pal/Content/Mods/PalworldPinItems/`. Widgets use native UMG and game-supplied engine fonts. Build and install include every Lua module, including `ui.lua`. ZIP creation is opt-in and requires the user's request. The standalone Windows cooking project disables the unused AndroidFileServer plugin so it does not generate a local security token into versioned configuration.

On 2026-10-10, all five Widget Blueprints compiled, and cooking completed with zero errors or warnings. Lua regression tests cover recipe snapshots, icons, owned/needed text, changing completion state, the five-card cap, retained additional pins, paging, tab injection, and menu closure. The prior version's workbench/B-menu pinning and live inventory counts were confirmed in-game after the FText crash fix. The user confirmed the redesigned UI works in-game, specifically that the HUD shows only five pins and the Pinned entry exposes six or more saved pins. Runtime logs confirm crafting pins, tab injection, and the Pinned view opening without mod errors. Palworld widget names and reflected signatures can change with game updates.
